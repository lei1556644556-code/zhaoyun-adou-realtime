# 迁移、发布与回滚

## Supabase 迁移顺序

权威台账为 `ops/migrations.json`，必须与 `supabase/migrations/*.sql` 一一对应并按时间戳升序。当前顺序：

1. `20260902133000_player_accounts.sql`：创建账号档案/云存档表、RLS 策略和 authenticated 权限；必须先于客户端 `0.1.0` 生产发布。

部署步骤：备份目标 schema 和受影响表；在 Preview 执行迁移；运行两账号隔离、匿名拒绝、插入/更新/读取测试；记录迁移 ID 与执行时间；生产维护窗口再次执行。不得由 PR 工作流自动持有数据库管理凭据。

## 应用发布

1. 确认 `pnpm verify`、07 验收和 Preview 迁移演练通过。
2. 同步 workspace 版本，更新变更说明并提交。
3. 在 main 的精确提交创建签名/受保护的 `vX.Y.Z` 标签。
4. 用 `Deploy GitHub Pages` 工作流发布该 SHA；验证 `/release-manifest.json` 与目标 SHA 一致。
5. 验证首页、登录、人机、房间、云存档和刷新恢复，保存工作流与验收链接。

## 回滚

- 客户端：手动运行 `Deploy GitHub Pages`，`ref` 填写上一个已验收 `vX.Y.Z` 标签。工作流会重新校验并构建该 ref，禁止从本机未提交目录上传。
- 数据库：默认只前向修复，先回滚应用到兼容版本。现有账号表含用户数据，未经备份和明确数据处置审批不得 `drop table`。
- 协议：客户端/服务器出现不兼容时先停止新服务器流量并恢复上一对兼容版本；不得只回滚一端。
- 回滚后：记录原因、受影响版本、数据库状态和恢复时间；修复走新的补丁版本，不移动旧标签。

## 发布检查

- [ ] 发布 SHA 的 CI 成功，`release-manifest.json` 版本/SHA/协议正确。
- [ ] 所有 Supabase 迁移已在 Preview 和生产按台账执行并留痕。
- [ ] Pages 环境变量只含 URL 与 publishable key，环境 reviewer 已启用。
- [ ] 桌面与手机布局、人机、双人、刷新、重连、退出和账号隔离通过。
- [ ] 浏览器控制台无启动错误，静态资源无 404，生产产物无 `.map`。
- [ ] 独立服务器发布时 `/health` 正常，Origin/TLS/状态策略与客户端目标一致。
- [ ] 上一个 release 标签仍可由手动工作流重建，数据库仍与其兼容。
